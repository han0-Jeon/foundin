# foundin

정부지원사업 공고를 대신 정독하는 에이전트입니다.

자격 요건은 꼭 흩어져 있습니다. 본문에 한 줄, 첨부 PDF에 한 줄, 붙임 HWP 각주에 한 줄. 그 한 줄을
놓치면 서류를 다 쓰고 나서야 압니다.

처음엔 요약만 붙이면 되는 줄 알았습니다. 그런데 요약은 그럴듯할수록 위험합니다. 열 줄 중 아홉 줄이
맞고 한 줄이 틀리면 사람은 그 한 줄을 못 골라냅니다. 원문을 다시 안 읽으려고 요약을 보는 건데,
요약을 검증하려면 원문을 다시 읽어야 하니까요. 잘 요약하는 것보다 지어내지 않는 게 훨씬 어렵습니다.

그래서 모델을 믿는 대신, 모델이 지어냈는지 기계가 확인할 수 있는 구조로 짰습니다. Upstage
Solar Open 2 가 공고 원문과 첨부를 읽고 자격·지원금·마감·서류·탈락 위험을 뽑되, 항목마다 원문
인용을 같이 달게 합니다. 그다음은 코드 차례입니다. 인용문이 원문에 실제로 있는지 전부 기계로
대조하고, 통과한 것만 발행합니다. 통과 못 한 항목은 조용히 사라지지 않고 "원문 확인 필요"로 남습니다.

이름은 founding 에서 g 를 하나 뺐습니다. found in 이기도 하고요.

[foundin.kr](https://foundin.kr) 의 분석 엔진이 이 저장소입니다. 서비스 워커와 여러분이 클론해서
돌릴 CLI 가 같은 코드를 씁니다.

결과물이 어떻게 생겼는지는 [examples/sample-brief.md](examples/sample-brief.md) 를 보시는 게
가장 빠릅니다. 실공고를 분석한 실물이고, 인용 23개가 전부 원문 대조를 통과한 건입니다. 손대지
않았습니다.

## 지금 돌아가고 있는 것

2026-07-28 프로덕션 실측입니다.

| | |
| --- | --- |
| 수집 공고 | 2,368건 · 소스 5곳 (K-스타트업 · 중기부 · 청년정책(온라인청년센터) · 콘텐츠진흥원 · 소상공인24) |
| 생성 브리프 | 550건 (발행 473 · 보류 56 · 반려 18 · 수집 실패 3) |
| 발행 기간 | 첫 브리프 2026-07-19, 가장 최근 2026-07-26 |

수집은 매일 새벽 5시(KST)에 돕니다. 발행은 매일 되지 않습니다. 새 공고가 올라와야 브리프도
생기니까요. 수집한 공고가 전부 큐에 오르는 것도 아닙니다. 2,368건 대비 브리프가 550건인 건
그래서입니다.

숫자 중에 정말 보여드리고 싶은 건 발행 473이 아닙니다. **발행까지 못 간 74건, 13.5%** 쪽입니다.

그중 셋이 이야깃거리입니다. 선입금이나 수수료를 요구하는 공고 2건, 개인 계좌 송금을 유도하는 공고
1건. 프리체크의 위험신호 스캔이 LLM 을 부르기 전에 잘랐습니다. 요약만 하는 파이프라인이었다면 이
3건은 아주 읽기 좋은 요약이 돼서 사용자 앞에 나갔을 겁니다.

나머지 반려 15건은 판정 단계에서 걸렀는데, 절반쯤은 예상대로 시설 소개나 포털 목록 페이지였고
나머지가 재밌습니다. "컨설턴트 모집", "협력기관 시스템 등록", "이미 선정된 회계법인 등록" 같은
것들. 지원사업 공고의 외형은 갖췄지만 수혜자를 뽑는 게 아닌 문서들입니다. 이 구분은 키워드로는
안 되고, Solar 가 문맥을 읽어서 낸 판단입니다.

보류 56건은 자격요건을 못 뽑은 게 35, 마감일을 원문에서 검증하지 못한 게 15, 인용 통과율 미달이 6.
전부 fail-closed 로 걸린 것이고, 그래서 사용자는 틀린 마감일 대신 아무것도 못 봅니다. 이 교환이
맞다고 생각합니다.

## 돌려보기

Node 20 이상이면 됩니다.

**Windows (PowerShell)**

```powershell
npm install
Copy-Item .env.example .env        # UPSTAGE_API_KEY 입력
npm run demo
```

**macOS · Linux (bash)**

```bash
npm install
cp .env.example .env               # UPSTAGE_API_KEY 입력
npm run demo
```

`npm run demo` 는 무엇을 분석할지 물어봅니다. URL 을 찾아 붙여넣지 않으셔도 됩니다.

```
무엇을 분석할까요?

  1) K-Startup 사업공고 목록
     개별 공고가 아니라 목록 페이지 — 반려되는 게 정상입니다
     https://www.k-startup.go.kr/web/contents/bizpbanc-ongoing.do

  2) 2026년 ICT혁신센터 입주기업 모집공고(상시)
     지금 접수 중인 실제 공고 — 정독하고 브리프를 만듭니다
     https://www.k-startup.go.kr/web/contents/bizpbanc-ongoing.do?schM=view&pbancSn=177493

  3) 직접 입력

선택 [2]:
```

**1번은 일부러 공고가 아닌 페이지입니다.** 이 파이프라인의 요점은 잘 요약하는 게 아니라 지어내지
않는 거라서, 판정 단계가 포털 목록을 반려하고 그 이유를 대는 장면이 발행된 브리프만큼 중요한
증거입니다. 2번은 지금 접수 중인 공고를 foundin.kr 사이트맵에서 무작위로 가져옵니다 — 별도 키가
필요 없고 매번 다른 공고가 나옵니다.

돌리면 단계별 진행이 이렇게 보입니다. 공고에 따라 추출이 수 분 걸려서, 어디까지 갔고 얼마나
지났는지 보이게 해뒀습니다.

```
    ✓ 수집       원문 1 · 첨부 3건                            1.2s
    ✓ 프리체크   공공 도메인 + 공고 패턴 9개 충족             0.3s
    – 판정       생략
  > ◐ 추출       조건·날짜·서류 추출          --*--       1m 33.4s
    · 검증       인용을 원문과 대조
    · 조언       처지별 판단 코멘트
    · 조립       브리프 조립

    3/7 단계 완료 · 경과 1m 35s · 남은 시간은 알 수 없습니다
```

진행 중인 줄만 `>` 로 왼쪽 여백을 뚫고 나옵니다. 색이 죽는 환경에서도 어디가 진행 중인지 보이라고
위치로 표시했습니다. 오른쪽 `--*--` 는 해가 좌우로 움직이며 광선이 뻗었다 줄어드는 자리인데,
진행률이 아니라 "돌고 있다"는 표시입니다. 추출 안쪽 진척은 알 수 없어서 진행률 막대를 두지
않았습니다 — 대신 남은 시간을 모른다고 적었습니다.

`판정 생략`은 프리체크가 공공 도메인임을 결정적으로 확인해서 Solar 호출을 하나 아꼈다는 뜻입니다.
파일로 리다이렉트하거나 CI 에서 돌리면 애니메이션 없이 한 줄씩 나갑니다. `--no-progress` 로 끄고
`--progress` 로 강제할 수 있습니다.

> Git Bash(mintty) 를 쓰시면 Node 가 터미널을 못 알아보는 경우가 있습니다. 위 화면 대신 한 줄씩
> 로그만 나오면 `--progress` 를 붙이세요.
>
> 한글이 글자마다 벌어져 보인다면 폰트 문제입니다. Git Bash 기본 폰트(Consolas 등)에 한글이 없어
> Windows 가 다른 폰트로 대체하는데, 그 글리프가 2칸 폭에 안 맞습니다. 우클릭 → Options →
> Text 에서 **D2Coding** 이나 **나눔고딕코딩** 처럼 한글 고정폭 글꼴로 바꾸면 정렬이 딱 맞습니다.

보고 싶은 공고를 직접 넣으시려면 이렇게 씁니다. 내 조건과 대조까지 하려면 프로필을 붙이세요.
이 JSON 은 로컬에서만 쓰입니다.

## 파이프라인

```
공고 URL
  → ① 수집: 원문 HTML + PDF·HWP·HWPX·DOCX 첨부 (SSRF 가드, EUC-KR 대응.
       암호화·DRM 문서만 "미분석" 표기)
  → ①.5 프리체크: 출처 도메인 티어(공공 *.go.kr·화이트리스트 / 일반 / 반려) + 위험신호
       (선입금·계좌 송금·주민번호·텔레그램 유도) + 공고 패턴. 전부 결정적 코드.
       공공 도메인의 정상 공고면 판정을 건너뛰고, IP·punycode·유사도메인·위험신호면 즉시 반려
  → ② 판정: 프리체크가 애매할 때만. 지원사업 공고인가?
  → ③ 추출: 자격·제외·서류·일정·위험 + 모든 항목에 원문 인용 (Solar Open 2)
  → ④ 검증: 코드가 인용·날짜·금액을 원문과 대조. 실패분은 피드백으로 되돌려 1회 재추출,
       그래도 안 되면 그 항목만 보류
  → ⑤ 게이트: 마감·자격 같은 핵심 필드가 깨지면 브리프 전체 미발행 (fail-closed)
  → ⑥ 조언: 검증 통과한 요건만으로 처지별 분기 조언 생성 (예비창업자라면 / 기창업자라면)
  → 판단 브리프 (JSON + Markdown)
```

## 몇 가지 설계 판단

### tool calling 은 되는데 안 씁니다

캘리브레이션 프로브에서 `solar-open2` 는 tool_calls 를 정상적으로 돌려줬습니다
([실측 리포트](eval/calibration-report.md)). 그런데도 러너 인터페이스는 "프롬프트 → 텍스트" 한
줄로 잘라놨습니다.

가장 큰 이유는 러너 교체입니다. 베타가 끝나면 `claude-code` 나 `codex` 구독 CLI 로 갈아타야 하는데,
이쪽은 서브프로세스라 함수 호출 스키마 같은 게 없습니다. 공통분모를 텍스트로 잡아두면 환경변수
하나로 갈아탈 수 있고, 실제로 그렇게 됩니다.

나머지 하나는 게이트 소유권입니다. 모델이 도구 호출 순서를 정하는 구조에서는 검증을 건너뛰는 경로가
원리적으로 존재합니다. 여기서는 오케스트레이터가 검증기를 무조건 마지막에 부르고, 발행 게이트는
모델이 볼 수 없는 곳에 있습니다. 발행 여부를 모델이 못 정하게 하는 게 이 제품의 전부라서 그
부분만은 코드가 쥐고 있어야 했습니다. 덤으로 실패한 응답이 그냥 문자열이라 픽스처로 박제해
테스트에 넣기도 쉽습니다.

### 검증은 LLM 이 하지 않습니다

`src/verify/` 는 전부 결정적 코드입니다. 인용문을 NFKC 정규화해서 원문에서 substring 으로 찾고,
표나 줄바꿈으로 쪼개진 원문 때문에 공백까지 지운 초정규화 대조를 한 번 더 겁니다. 날짜와 금액은
인용문에서 값을 다시 파싱해 모델이 적어낸 값과 맞춰봅니다. 여기서 걸리는 게 환각 인용입니다.

라이브에서 두 건만 비교해보시면 차이가 보입니다. foundin.kr 의 "성남 소공인특화지원센터 기술 컨설팅
공고"는 인용 24개가 전부 통과했고, "2026 딥테크 스튜디오 공고"는 28개 중 27개입니다. 실패한 1건은
지워지지 않고 보류로 남아 "기관에 물어볼 질문"으로 바뀝니다. 검증 실패를 숨기는 것보다 넘기는 편이
낫다고 봤습니다. 둘 다 [/programs](https://foundin.kr/programs) 에서 직접 보실 수 있습니다.

### 프로필은 모델에 보내지 않습니다

조건 대조는 `src/match/` 의 결정적 규칙이 로컬에서 합니다. Solar 로 가는 건 공개된 공고 원문뿐입니다.
그럼 개인화는 어떻게 하느냐. 공고 쪽에서 "예비창업자라면 / 기창업자라면" 식 분기 조언을 미리
만들어두고, 클라이언트가 자기 분기만 렌더합니다. 개인화 체감은 얻고 프로필은 안 나가는 절충입니다.

공고문에 흔히 박혀 있는 담당자 이름·전화·이메일도 `src/collect/contact.ts` 가 모델에 보내기 전에
마스킹합니다. 화면에 띄울 값은 코드가 따로 뽑아 브리프에 담습니다.

### HWP 는 직접 뜯었습니다

한국 공공 공고 첨부의 사실상 표준인데 제대로 읽어주는 게 마땅치 않았습니다. `.hwp` 는 CFB 컨테이너를
열어 BodyText 스트림을 레코드 단위로 걸고 `HWPTAG_PARA_TEXT` 의 UTF-16LE 본문만 뽑고, `.hwpx` 는
OWPML XML 에서 `<hp:t>` 노드를 모읍니다(컨테이너 해제에는 `cfb`·`fflate` 를 씁니다). 100건 평가에서
미분석으로 남은 24건 중 HWP 계열은 0건이었습니다. 암호화·DRM 문서는 읽을 수 없어서 그대로
"미분석"이라고 적습니다.

## Solar Open 2 를 실전에서 써본 소감 (Partner Stage 1)

| 항목 | 값 |
| --- | --- |
| 모델 | `solar-open2` (Upstage Private Beta, 2026-07-17 ~ 07-31) |
| Rate Limit | 400 RPM / 150,000 TPM |
| Console | https://console.upstage.ai |

키를 받자마자 캘리브레이션부터 돌렸습니다. JSON 스키마 준수 5/5, 30K 짜리 장문에서 마감일 정확히
추출. 검증 파이프라인의 추론 엔진으로 세워도 되겠다 싶어서 실공고 100건 배치로 넘어갔습니다.

첫 라운드 발행이 26건이었습니다. 78이 아니라 26.

그런데 뜯어보니 대부분 제 코드 문제였습니다. 여덟 군데를 고쳤고, 그중 몇 개는 이렇습니다.

- K-Startup 마감 공고가 빈 셸 페이지로 응답 → ongoing↔deadline 형제 경로 폴백
- 제출 URL 정규화가 상세 화면 파라미터(`schM=view`)를 지워버리던 결함
- 위험신호 스캔이 첨부 신청서의 표준 문구에 오탐 → 랜딩 문서로 한정
- 장문 추출 타임아웃 180초로는 부족 → 300초

제일 오래 잡아먹은 건 응답이 통째로 비어서 오는 현상이었습니다. 추론 모델이라는 고지가 없어서
한참 헤맸는데, max_tokens 가 빠듯하면 내부 추론만 하다가 예산을 다 쓰고 빈 문자열로 끝나더군요.
버퍼를 늘려 재시도하는 코드를 직접 넣어서 막았습니다.

마지막 라운드 결과는 이렇습니다([평가 리포트](eval/REPORT-2026-07.md)).

- 발행 78건. 표본 전체로 78.0%, 공고가 아니었던 9건을 뺀 유효 공고 기준 85.7%(78/91)
- 인용 원문 대조 평균 통과율 92.0%
- 환각 인용이 검증을 뚫고 발행된 사례 0건
- 베타 기간 누적 약 568만 토큰, 비용 $0

좋았던 점은 한국어 행정문서 독해입니다. "예비창업자"를 사전적 의미가 아니라 정부지원사업 문맥
그대로 이해했고, 구조화 출력이 안정적이라 tool calling 없이도 파이프라인의 추론 엔진으로 세울 수
있었습니다. 아쉬운 건 지연입니다. 구조화 출력 프로브 5회가 호출당 15~27초였고, 장문 추출은 300초
타임아웃이 필요했습니다. 빈 응답 문제도 고지가 있었으면 하루는 아꼈을 겁니다. 다만 둘 다
애플리케이션 설계로 흡수되는 종류의 결함이었습니다.

하니스 숫자와 프로덕션 숫자를 나란히 놓을 때는 조심하셔야 합니다. 100건 하니스의 78.0%(78/100)와
프로덕션의 86.0%(473/550)는 분모 구성이 다릅니다. 하니스 100건에는 비공고 9건과 수집 실패 5건이,
프로덕션 550건에는 반려 18건과 수집 실패 3건이 섞여 있습니다. 같은 지표라고 말할 수 없고, 5.5배
규모에서 비슷한 대역이 재현됐다 정도로 읽는 게 맞습니다. 평가 하니스는 그대로 두고 있어서,
Solar Pro 4 가 나오면 같은 100건으로 개선 폭을 다시 재볼 생각입니다.

한 가지 더. 골든셋 대비 필드 정확도는 아직 측정하지 않았습니다. 위 숫자들은 "인용이 원문에
실재하는가"이지 "추출된 값이 정답인가"가 아닙니다.

## 저장소 구조

```
src/
├── agent/        오케스트레이터 + 프롬프트 (프리체크 → 판정 → 추출 → 조언)
├── verify/       결정적 검증기: 인용 대조 · 날짜/금액 재파싱 · 충돌 · 발행 게이트
├── collect/      SSRF 가드 fetch · HTML/PDF/HWP/HWPX/DOCX 텍스트 추출 · EUC-KR 디코드
│                 · precheck(도메인 티어·위험신호) · contact(연락처 마스킹)
├── llm/          러너 추상화: solar (베타) | claude-code | codex (구독 CLI)
├── match/        로컬 프로필 매칭 (LLM 비전송)
├── brief/        브리프 렌더러 (Markdown/터미널/MCP)
├── cli.ts        analyze · today
├── mcp.ts        MCP 서버 (experimental)
└── worker.ts     foundin.kr 큐 폴링 워커 (Supabase Realtime 즉시 깨우기 + 20초 폴링 폴백)
eval/calibrate.ts 모델 캘리브레이션 (JSON 준수율·장문·지연·tool calling 프로브)
eval/batch.ts     배치 평가 하니스 (지표 전용, 발행하지 않음)
fixtures/ test/   오프라인 픽스처와 테스트
```

궁금한 동작은 대개 `src/verify/` 를 열어보시는 게 이 문서를 더 읽는 것보다 빠릅니다.

## 다른 에이전트에서 도구로 쓰기 (MCP, experimental)

MCP 서버가 들어 있습니다. Claude Code·Cursor 같은 클라이언트에 물려두면 대화 중에 공고 분석이
필요할 때 에이전트가 이 검증 파이프라인을 도구로 부릅니다. 대화층은 사실을 만들어낼 수 없고,
원문 대조를 통과한 도구 출력만 받습니다.

```jsonc
// 예: Claude Code 의 .mcp.json
{ "mcpServers": { "foundin": { "command": "npm", "args": ["run", "mcp"], "cwd": "<클론 경로>" } } }
```

도구는 셋입니다. `analyze_announcement(url)` 정독·검증 브리프, `check_eligibility(url, profile)`
조건 대조, `today(urls, profile)` 우선순위 브리핑.

`analyze_announcement` 는 논블로킹입니다. 처음 보는 URL 은 백그라운드 분석을 시작하고 "진행 중"을
즉시 돌려주며, 4~6분 뒤 같은 URL 로 다시 부르면 완료본이 옵니다. 캐시된 공고는 바로 나옵니다.
MCP 클라이언트 타임아웃이 대개 5분이라 이렇게 만들었습니다.

붙이기 전에 알아두시면 좋은 것들:

- LLM 비용은 본인 키로 나갑니다. 베타 키가 없으면 `.env` 에 `UPSTAGE_MODEL=solar-pro3` 처럼 일반
  콘솔 키로 쓸 수 있는 모델을 지정하세요
- 도구 출력에는 담당자 연락처가 들어가지 않고, 원문 인용은 "지시 아님" 데이터 블록으로 격리됩니다.
  다만 채팅창에 직접 입력하신 내용은 본인 에이전트의 대화로 그대로 갑니다. 그 경계는 사용자 몫입니다
- 신뢰하지 않는 URL 을 분석시킬 때는 에이전트의 파일·셸 권한을 좁혀두시길 권합니다. 외부 문서를
  읽는 도구의 공통 주의사항입니다
- experimental 이라 인터페이스가 바뀔 수 있습니다. 이슈 대응은 베스트 에포트입니다
